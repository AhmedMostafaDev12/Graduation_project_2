# backend-ai — Database (local Postgres, Supabase, Alembic)

Tables: spec §6 (the ERD is in `docs/diagrams/02-database-erd.md`). Hosting decision: spec D25.

---

## 1. Two databases, one schema

| | Local (development) | Supabase (production / demo) |
|---|---|---|
| What | Docker `pgvector/pgvector:pg16` | Supabase project, PostgreSQL 16 + pgvector, EU (Frankfurt) |
| Who uses it | every developer, every test run | the deployed API and workers on EC2 |
| Connection | `postgresql://remori:remori@localhost:5432/remori` | Supabase **direct** or **session pooler** string + `sslmode=require` (not the transaction pooler) |
| Data | seed script (the UI brief's sample data) | real data |

`DATABASE_URL` in `config.py` is the **only** difference. Never develop or run tests against Supabase.

Start local Postgres (outside Compose):
```bash
docker run -d --name remori-db -p 5432:5432 -e POSTGRES_USER=remori -e POSTGRES_PASSWORD=remori -e POSTGRES_DB=remori pgvector/pgvector:pg16
```
pgAdmin: connect to `localhost:5432` with the same credentials.

## 2. Supabase rules (spec D25)

- **Plain Postgres only.** Don't use Supabase Auth, Storage or the auto-generated Data API.
- **Turn off the Data API** in project settings, and **enable RLS with no policies** on every table. Data is reachable only through FastAPI.
- **Users:** `postgres` (owner) runs migrations · `remori_app` for the API and workers (read/write, no DDL) · `remori_readonly` for teammates (SELECT only).
- **Team access:** Supabase dashboard (table + SQL editor) or pgAdmin with the readonly connection string. Never commit connection strings.
- **Free tier:** the project pauses after about a week without activity (unpause from the dashboard) and has a small size quota. Take a `pg_dump` before every demo.

## 3. Alembic (migrations)

As in the course, plus these points:
1. **Migrations are the only way to change the schema.** Never edit tables by hand in pgAdmin or the Supabase dashboard.
2. **First migration:** `CREATE EXTENSION IF NOT EXISTS vector;`
3. **Always read the autogenerated migration** before committing. Autogenerate misses some changes (enum values, server defaults, some index changes).
4. **Postgres ENUMs:** adding a value needs a hand-written `ALTER TYPE … ADD VALUE`. Autogenerate won't do it.
5. **Order:** run `alembic upgrade head` locally → tests pass → merge → then the lead applies it to Supabase.
6. **One migration per PR**, named for what it does. Never edit a migration that's already merged; add a new one.
7. A new table or column must already be in spec §6. If it isn't, ask the lead (contract-first).

## 4. Column conventions (spec §6)

| Rule | Detail |
|---|---|
| Primary keys | UUID. Records created on the glasses/phone keep the client's UUID |
| Timestamps | `TIMESTAMPTZ`, always UTC |
| Sync columns | `updated_at` + `deleted_at` (soft delete) on every table the phone syncs |
| Enums | Postgres ENUM, lowercase snake_case values exactly as spec §6 |
| Flexible fields | `JSONB` only where the spec says so (`metadata`, `ai_tags`, `extracted_fields`, `patterns`) |
| Vectors | `VECTOR(512)` faces, `VECTOR(1536)` text, HNSW index with cosine distance |
| Names | snake_case, plural table names, as spec §6 |
